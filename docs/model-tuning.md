# 智能家居场景的模型调优：提示词、微调与评测

2026-08-16 沉淀。回答一个具体问题：**「怎么控制设备、怎么回答」这类知识，值不值得训进模型？**

结论先行：**回复风格不值得微调；真正值得微调的只有「把模型做小」这一件事；
而在动手微调之前，你缺的是评测集，不是数据。**

---

## 一、先问：这个问题该用哪个杠杆

同一个毛病往往有多个解法，成本差一两个数量级。动手前先对号入座：

| 杠杆 | 成本 | 适用 | 反例 |
|---|---|---|---|
| **提示词** | 分钟级，改完立刻生效 | 回复风格、长度、追问时机、术语禁令 | 解决不了模型的能力上限 |
| **实体命名 / 别名** | 小时级 | 识别率、歧义、token 体积 | 见 `voice-tuning.md` |
| **暴露面** | 小时级，一次性 | 延迟、准确率、安全边界 | 见 `exposure-policy.md` |
| **模型采样参数** | 分钟级（Modelfile） | 退化循环、输出长度硬上限 | 改不了语义行为 |
| **架构**（分层路由、动态发现） | 天级 | 延迟、可用性、上下文体积 | 见 `blueprint.md` 第 03 节 |
| **微调** | 周级 + 长期维护 | **只有上面全都不够用时** | 模型一升级就作废 |

**能用上面五个解决的，就不要用微调。** 这条在本项目里被反复验证：
回复长度失控、无限循环、追问过度、内部术语泄漏 —— 四个问题全部由提示词和采样参数解决，
没有一个需要动模型权重。

---

## 二、回复风格：用提示词，不要微调

三条理由：

**1. 模型一升级就作废。** Qwen3.5 出来要重新造数据、重训、重测；
提示词直接复制过去就能用。本地部署的模型两三个月就该跟一次版本。

**2. 省不了多少 token。** 本宅的行为约束约 100 token，占 prompt 总量 2543 的 **4%**。
微调把它省掉，收益可以忽略。

**3. 改一条规则的成本差三个数量级。** 想加「执行后不要反问」：
提示词改一行、三十秒；微调要重新造数据、重训、重测，还得担心回归。

本项目的提示词迭代过程见 `voice-tuning.md` —— 四版收敛，全程没碰模型权重。

## 三、微调真正值得的方向

### ① 把模型做小（唯一有说服力的理由）

微调在这个场景下的正当用途，**不是让模型更聪明，是让它更小而不变笨**。

| | 现状（Qwen3-8B Q4） | 目标（微调后的 1.7B / 3B） |
|---|---|---|
| 显存 | 6.4 GB | 约 2 GB |
| 端到端延迟 | 1.0–1.2s | 约 0.4s，接近反射层 |

腾出的 4 GB 可以给别的模型（视觉、更大的 TTS），延迟则直接改善体感。

[acon96/home-llm](https://github.com/acon96/home-llm) 整个项目就是这个思路 ——
Home-1B / Home-3B 专为 HA 控制微调，无 GPU 也能跑。想走这条路，先读它的
[Model Prompting](https://github.com/acon96/home-llm/blob/develop/docs/Model%20Prompting.md)
和训练脚本，别从零开始。

### ② 工具调用的稳定性（与 ① 捆绑，单独做没意义）

8B 的工具调用已经够稳 —— 实测函数名和 `area` / `domain` 全对，
唯一的问题是偶尔编造不存在的 `name`（「关书房的灯」填了 `name:"台灯1"`）。
这个用提示词约束 + 实体命名治理就能压下去。

但降到 1.7B 就不行了。[mcp-assist](https://github.com/mike-nott/mcp-assist)
的作者明确写着「4B 模型工具调用会失败」，推荐 8B 以上。

**所以 ① 和 ② 是捆绑的**：想用小模型就必须微调工具调用，
否则省下的延迟会被错误率吃回去。反过来，如果你不打算做小，就没必要微调工具调用。

### ③ TTS 音色：本宅不需要

之前误判过一次：把曼波音色的 `sh`→`x`（书房→修房、猫砂→猫虾）
当成了「需要修复的发音缺陷」。**其实那就是这个角色音色本身的特点**，不该改。

什么情况下才值得做 TTS 微调：

- 想要一个**全新的、稳定的**自制音色，而 zero-shot 的相似度不够
- 同一音色在长文本上音色漂移明显

不值得做的情况：

- 「某几个字念得不标准」—— 如果那是角色特征，改了反而丢了辨识度
- 只是想换个音色 —— 换参考音频做 zero-shot 就行，成本低两个数量级

## 四、如果真要微调，数据长什么样

### 样本格式

一条样本 = 一次完整的交互，**必须包含系统上下文**，因为模型要学的是
「在给定的实体清单下如何选择」，而不是「怎么说话」：

```
system:  <行为约束> + <实体清单：名称/域/区域/状态>
user:    把书房的灯关掉
assistant: <tool_call> HassTurnOff(area="书房", domain=["light"])
tool:    {"success": [...]}
assistant: 书房的灯关好了。
```

### 必须包含负例（最容易被忽略的一条）

只喂正样本，模型会学成「什么都答应」。以下四类负例同等重要：

| 类型 | 期望行为 |
|---|---|
| 设备不存在 | 说找不到并反问是哪个房间，**不要编实体名** |
| 指代不清（「把那个关了」） | 反问，不要猜 |
| 超出能力（「帮我订披萨」） | 直说做不到 |
| **不该执行的**（「把所有灯关了」而植物灯在列） | 执行范围要正确排除 |

最后一类是安全相关的，本宅的植物灯/生态缸约束就属于这类。

### 数据量

LoRA 微调 8B：**1k–5k 条**起步。
从零训小模型不现实，只能在开源小模型上做 LoRA。
acon96 的做法是**合成数据生成** —— 用大模型批量造「指令 + 正确工具调用」对，再人工抽检。

### 数据从哪来：你已经在攒了

HA 的 `assist_pipeline/pipeline_debug` 里有完整的交互记录：

```
WebSocket: assist_pipeline/pipeline_debug/list  {pipeline_id}
           assist_pipeline/pipeline_debug/get   {pipeline_id, pipeline_run_id}

事件序列: run-start → stt-end（识别文本）
                    → intent-progress ×N（LLM 增量输出）
                    → intent-end（工具调用 + 回复）
                    → tts-end
```

这是**你家真实的说话方式**，比任何合成数据都贴合。

⚠️ **HA 只保留最近若干次运行**，要用就得定期导出归档。
建议现在就开始存 —— 攒几周才有量，而且早期数据反映的是「系统还不完善时用户怎么说」，
恰恰是最有价值的部分。

## 五、评测集：优先级高于微调

**2026-08-16 更新：已建成，见 `scripts/eval_cases.yaml` + `scripts/run_eval.py`。**
20 条用例，跑一轮（每条 3 遍）约 80 秒。下文保留了当初判断它「优先于微调」的推理，
末尾补上真正建起来之后踩到的坑 —— 那几个坑比用例本身更值钱。

本项目调了四版提示词，每版都是**手工跑四条指令**验证的。后果：

- 不知道 v4 有没有在别的场景上比 v3 差
- 换模型、改提示词、加设备之后，没有任何东西告诉你是变好还是变坏
- **微调更是如此 —— 没有评测集，微调就是盲调**

### 三类断言

| 类 | 例子 | 回归了会怎样 |
|---|---|---|
| **正确性** | 调对函数、对区域、对实体 | 功能坏了，当场能发现 |
| **风格** | 字数 ≤40、该不该追问、无 Markdown、不泄漏内部术语 | 体验变差，但不易察觉 |
| **安全** | 植物灯不被「关所有灯」波及；门锁不可控 | **事故，且可能很久才发现** |

第三类最重要。本项目做的所有暴露面治理，**目前没有任何东西防止它被回滚** ——
哪天加个设备、点错个开关，植物灯又进了暴露集合，没人会知道。

### 起步规模

四五十条足够。覆盖：

```
高频指令      开灯关灯、调温度、查状态          10 条
模糊表达      「有点冷」「太亮了」              5 条
范围操作      「关掉所有的灯」「客厅都关了」      5 条 ← 安全断言在这里
查询类        「几点了」「灯开着吗」            5 条
概况类        「家里什么情况」+ 展开/继续        5 条 ← 风格断言在这里
异常输入      不存在的设备、指代不清、超纲请求    10 条
多轮          上下文指代（「再暗一点」）         5 条
```

### 与微调的关系

顺序不能反：

```
1. 评测集      → 半天工作量，立刻能用
2. 归档真实数据 → 攒几周
3. 微调         → 只有当 1 证明提示词已到极限、2 有足够数据时
```

**先有尺子，再谈改进。**

### 造尺子时踩的四个坑

这套东西第一版跑出来 10/16，其中**四条失败是尺子自己的毛病**，不是助手的。
如果当时直接信了那个分数，接下来的调优全是错的方向。

**① 断言不能看 `response.data.success`**

内建意图代理返回结构化的 `data.success[]`（受影响实体清单），
**LLM 对话代理返回的是纯文本**，工具调用结果根本不在里面。
按这个字段断言「有没有影响到某设备」，对 LLM 代理**恒为失败**。

改成看**实体的真实状态**：跑之前记一份，跑之后再读一份，比对。
顺带解决了安全断言 —— 「植物灯有没有被波及」本来就该看灯，不该看助手怎么说。

**② 状态回报有延迟，单次读会误判**

MIoT 设备实测约 0.5s 才把新状态报回 HA。指令发完立刻读，读到的是旧值，
看起来就像「模型没执行」。要**轮询到期望状态或超时**，别读一次就下结论。

**③ ⚠️ `conversation_id` 必须每轮换新的（最坑的一个）**

一开始把它写死成 `eval-<用例id>`。结果：改了提示词重跑，**回复字节完全不变**。
因为 HA 按 `conversation_id` 保存会话历史，上一次跑的问答还在上下文里，
同一个问题再问一遍，模型直接把上次的答案复读一遍。

表现出来就是「提示词改了没生效」，很容易让人跑去查配置、查缓存、查模型加载。
实际上是评测**被自己污染了**。

**④ 单次跑分不可信 —— 这是个随机系统**

同一版提示词、同一套用例，连跑三轮拿到 **18/18、15/18、16/18**。
温度 0.7 下「通过/不通过」这个二元结论本身就不成立。

所以运行器改成**每条默认跑三遍报通过率**，输出分三档：

```
✅ 3/3  稳定通过
⚠️ 2/3  不稳定 ← 最该关注的一档，手工测十有八九碰不到
❌ 0/3  真的坏了
```

回归的判定也从「True→False」改成「通过率下降」。
**没有这一步，你会把运气当成结论**——第一次跑出 18/18 的时候我差点就信了。

### 用例里的两条家庭约束

评测集会真的去操作设备，所以它同时是一份**安全清单**：

- **不许出现卧室的任何设备** —— 有人在睡觉。跑一轮 `--repeat 3` 就是九次开关。
- **不许拿空调、压缩机类设备做 setup** —— 反复启停伤硬件。
  感受类用例因此只断言「不许编造房间名」这种与设备状态无关的部分。

这两条写在 `eval_cases.yaml` 顶部。**可控 ≠ 可以随便控**，
在家庭场景里这是和「断言写得对不对」同等重要的事。

## 六、本项目的建议顺序

```
① 建评测集（四五十条）                     ← 没有它，后面全是盲干
② 归档 pipeline_debug 数据                 ← 现在就开始，攒几周
③ 用评测集守住已有成果（暴露面、提示词）      ← 防回归
④ 等 ① ② 都到位，再评估要不要把模型做小
```

**第 ④ 步大概率永远不用做。** 1.0–1.2s 已经够用。
真正会逼你做的场景是「想同时跑 LLM 和别的大模型，显存不够了」——
那时才是微调登场的时候。
