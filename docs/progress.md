## 2026-08-17 · 播放链路修复与语音硬件协同设计

- **WSLg 音频桥的边界查明**：只要麦克风在采集，WSLg 的播放就慢 2.5~4 倍，换播放工具救不了（采集单独走是好的，坏的只有并发）。播放绕到 Windows 原生 `Media.SoundPlayer`（`scripts/snd_windows.sh`）后恢复正常 —— 但**牺牲了流式**，是权宜之计不是终局 → `deploy/README.md` 第十六节
- **TTS 首块延迟 5.54s → 1.28s**：断句取的是缓冲区**最后**一个停顿（`max()` 写反了），第一段被撑成巨块，流式形同虚设。改成取最早可用断点 + 首段 6 字阈值 + 60 字硬切兜底；同时补上「首块延迟 / 每句实时率 / 总耗时 vs 音频总长」三个指标——此前没有任何数字能说明流式到底有没有生效 → `docs/voice-tuning.md` 第三节
- **一条排查方法论**：这个环境的音频测量噪声比信号大，单次「命令耗时」把流启动、播放、进程滞留三段混在一起，同一条命令能测出 7 秒和 34 秒。有效的只有录 sink 监听端 + `silencedetect` 定位，以及人耳区分「没声音」和「断成两段」

- **安卓终端三合一方案定案**：Fully Kiosk + voice-satellite-card 单 App 实现屏+嘴+耳；HTTPS 列为前置闸门；旧手机管「有屏的点位」→ 蓝图第 11 节
- **触屏小爱刷机复活线**：LX04 刷机后 Fully media_player 播 URL，「小爱音色锁死云端」的弃用判决撤销,可作曼波音色播报点 → 蓝图第 11 节

- **多卫星/多音箱协同方案定案**：先到先得仲裁的坑与应对、Music Assistant 做播放总线、「卫星管听音箱管说」解耦原则 → 蓝图第 09 节
- **闲置 ESP32-S3 套件立项**：书房桌面卫星 + 播报出口，唤醒词复用服务端；记下 MAX98357 不可接线电平（换 PCM5102A）的硬件坑;曼波玩偶(屏幕当脸、表情=管线状态)列为延伸待办 → 蓝图第 09 节

## 2026-08-16 · 语音层从蓝图变成现实

- **语音栈全链路跑通**：faster-whisper STT（热态 0.30s）+ Ollama Qwen3-8B（对话端到端 1.0–1.2s）+ 曼波音色 Wyoming TTS（真流式，首字 0.30s）→ `deploy/README.md`
- **中文唤醒词「你好曼波」**：openWakeWord + wyoming-satellite 跑通，自训管线（数据生成→训练→导出）贯通验证；**同日推翻**——改用 sherpa-onnx 开放词表 KWS，33 MB 模型顶掉 16.5 GB 训练数据，换唤醒词只改一行文本（内部是带调拼音不是汉字），Wyoming 封装没现成的自己写 → `deploy/README.md` 第十五节
- **唤醒词评测集**：168 正样本 / 616 对抗样本扫 threshold × score，两个旋钮的行为都反直觉——threshold 六个取值召回率一个数没变，score 调高反而伤召回；平台区落在 score 1~2 / threshold 0.25，普通话召回 100%、误唤醒 0.17%（粤语 0%，暂不覆盖）→ `scripts/eval_kws.py`
- **暴露面治理**：435 → 83 实体（prompt ~14.2K → ~2.3K token），沉淀官方规则之外的 8 条判定规则；`expose_new` 关闭；switch_as_x 转 24 个继电器为 light/fan → `docs/exposure-policy.md`
- **提示词收敛**：v4 → v16 迭代 + 20 条评测集（走真实 `assist_pipeline/run`），稳定通过 18 条 → `docs/voice-tuning.md`
- **蓝图两处修正**：查明 `prefer_local_intents=True` 就是反射层，自建分层路由一步作废；新增第 14 节认知层框架设计
- **两个否决记录**：TTS 层硬分页（截断策略必须由知道意图的层来定）；全惰性检索 MCP Assist 类方案（多跳工具链是小模型最短板）
- **容量结论**：8B 实体甜点区 80–150、上限 ~250；4B 甜点区 40–80 → `docs/exposure-policy.md`
