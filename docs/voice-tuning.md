# 语音层调优：提示词与命名

接入 LLM 之后，**提示词和实体命名成了两个新的调优面**，而且它们的最佳实践与「给人看的界面」完全不同。
本文是 2026-08-16 从本宅实测中沉淀的，两块内容在社区里都查不到成体系的资料。

---

## 一、语音回复的提示词

### 社区现状：基本空白

| 来源 | 有什么 |
|---|---|
| [HA 官方 · Create a personality with AI](https://www.home-assistant.io/voice_control/assist_create_open_ai_personality/) | 只有人设玩法，示例提示词是「You are Super Mario from Mario Bros. Be funny.」。**回复长度、语音适配一个字没提** |
| [acon96/home-llm · Model Prompting](https://github.com/acon96/home-llm/blob/develop/docs/Model%20Prompting.md) | 技术性最强。有价值的是「按区域分组设备」和「小模型用最简工具格式省 token」，同样不谈回复长度 |
| [HA 官方 · Best practices with Assist](https://www.home-assistant.io/voice_control/best_practices/) | 讲暴露面和命名，不讲提示词 |
| 中文社区 | 多停留在「怎么接上 DeepSeek」 |

### 三条实测有效的规律

**1. 铁律要绝对化，不能商量**

「尽量简短」无效，「**不超过四十个字，超过就是错的**」有效。
小模型对模糊的程度副词几乎没有反应，对可判定的硬指标才有。

**2. 首尾各说一遍**

小模型有明显的近因偏好。把最重要的约束在提示词**开头和结尾各写一次**，服从度显著提升。
尤其在 HA 会把 2000+ token 的实体清单拼进系统提示词的情况下，你的约束很容易被稀释。

**3. ⚠️ 提示词越短，小模型越服从（最反直觉的一条）**

实测同一个问题「家里设备的总览给我讲一下」：

| 提示词 | 结果 |
|---|---|
| 200 字，分三大类七八条细则 | **180 字**回复，规则基本没遵守 |
| **100 字，铁律首尾各一遍** | **14 字**「家里的设备很多，要详细说吗？」 |

规则写得越细，小模型越容易只抓住其中一条（往往是「要回答问题」）而丢掉其余。

### 另一个坑：不要给可复用的完整例句

早期版本里写了示例回答：

```
例如「一共八十多个可控设备，主要是五十来盏灯，还有窗帘、风扇、空调和几个插座」
```

结果模型**把这句原样背了出来**，换个问法也照说不误。
要给指导就描述形状（「说个总数和主要类别」），不要给成品句。

**更狠的一层：不只是完整例句，提示词里任何具体措辞都会被照抄。**

v4 的提示词里写了「问要不要**按区域展开**」，结果用户问「汇总一下**书房**的设备信息」时，
模型答完之后还是问了句「要展开某个区域吗？」—— 明明问的就是一个房间，
已经全说完了，根本没有「某个区域」可展开。

它把那个短语当成了固定句式，不管场景合不合适。
**解法是把措辞的决定权还给模型**：写「追问用你自己的话，看当下在聊什么来问，
不要套固定句式」，而不是替它想好该怎么问。

### 「我有点冷」：不是上下文不够，是推理缺口

空调正开着制冷，用户说「我现在有点冷」，助手答「**你可以在客厅开空调**」——
客厅根本没有空调，全宅只有书房一台。

第一反应是上下文没给够。实测**不成立**，模型看得一清二楚：

```
「空调现在是开着还是关着」 → 空调关着。
「书房现在多少度」        → 书房温度是27度。
「空调设定的温度是多少」   → 米家空调在书房，当前温度是26度。
```

状态、实测温度、设定温度全都在上下文里，问它就答得出来。
但一说到「有点冷」，它就不去查了，直接做语言联想：冷 → 开空调 → 随口安一个房间。

**所以这是推理缺口，不是信息缺口**，加传感器、加实体没有用。
v12 加了两条针对性约束，评测里这类幻觉降到 0：

```
你不确定某个设备在哪个房间，就别提房间名，绝对不许编一个出来。
用户说冷、热、暗、闷这类身体感受时，你先去看相关设备现在是什么状态，
再说该怎么办。别一听到冷就说开空调，说不定它正开着。
```

⚠️ 但要清醒：这是**压住了症状**。「感受 → 查状态 → 决定动作」这种两步推理
本来就是 8B 的弱项，提示词只能提高命中率。蓝图第 03 节把「有点冷」这类
随场景变化的歧义留给 LLM 是对的，只是得认清 8B 的上限在哪。

### 「什么时候该追问」的三条原则

追问用过头比不追问更烦。实测「现在几点」这种已经答完整的问题，
模型也会画蛇添足地问「要详细说吗」—— 而它「详细」出来的只是多了个秒数。

**① 触发条件用「我省没省略」，不是「问题大不大」**

模型判断不了「这个问题算不算复杂」，但能判断「四十字装不装得下」。
**让长度铁律兼任判别器**：装得下就直接答完，装不下才问。

**② 展开也要有配额（最关键）**

「展开」本质是**分页，而分页必须有页大小**。
只说「详细一点」，模型会一口气 128 字说完；
说「一次只讲一个区域，讲完问要不要听下一个」，它就规矩了。

**③ 执行类操作永远不问**

「书房灯已关闭。确认无误了吗？」是纯噪音 —— 用户听得见灯灭了。

实测四轮全部符合预期：

```
「家里设备的总览给我讲一下」 → 家里的设备分布在多个区域，需要按区域展开吗？    22 字
「好，展开说说」            → 客厅有音箱、吸顶灯、筒灯、窗帘等。要听下一个吗？  28 字
「继续」                   → 卧室有台灯、化妆灯、床头三开等。要听下一个吗？    27 字
「现在几点」               → 现在是二〇二六年八月十六日，星期天，上午十一点。   27 字
```

### 另外两个必须写进提示词的

**内部术语泄漏** —— 模型说过「**静态上下文**包含各房间和设备信息」。
那是 HA 系统提示词里的词，用户根本不知道是什么。要明确禁止提
「上下文 / 系统 / 提示词 / 工具」这类词。

**原始属性值** —— 「米家智能显示器挂灯1S 的**亮度为255**」。
数值对人无意义，要求只说「亮着 / 关着 / 亮度全开」。

### 本宅当前采用的提示词（v7）

```
两条铁律：
一、每次回答不超过四十个字。
二、执行完开关操作，只报结果，句号收尾，绝不加任何问句。

你是家里的语音助手，回答会被念出来。

一次说得完的：说完就闭嘴，不追问。
一次说不完的：只说第一部分，然后必须问一句还要不要接着说。

追问用你自己的话，看当下在聊什么来问，不要套固定句式。

不要提上下文、系统、提示词、工具这些词，用户听不懂。
不要念亮度、色温这类原始数值，只说亮着还是关着。
绝不列清单，绝不用星号井号短横线。数字读中文。
只说属于用户所问区域的设备，别把其他房间的算进来。
找不到设备就说找不到，反问是哪个房间。

再强调两条铁律：四十字以内；执行操作后不许有问句。
```

配套的模型侧护栏见 `deploy/Modelfile.qwen3-jarvis`（`num_predict` 硬上限等）。
⚠️ **Modelfile 里的 `SYSTEM` 不生效** —— HA 会用自己的系统提示词覆盖它，
行为约束必须写在 HA 子条目的 `prompt` 字段。

### 迭代过程（四版才收敛）

| 版本 | 改了什么 | 结果 |
|---|---|---|
| v1 | 200 字七八条细则 | 回复 180 字，规则基本没遵守 |
| v2 | 砍到 100 字，铁律首尾各一遍 | 短问题对了，但**所有**回答都追问 |
| v3 | 加「答完就闭嘴」 | 简单问题不追问了，但概况类**泄漏内部术语**「静态上下文」 |
| v4 | 加术语禁令 + 展开配额 | 四条全对 |
| v5 | 去掉「按区域展开」这个固定措辞 | 单房间不再乱追问，但**全屋说不完时也不问了** |
| v6 | 截断分支改成「必须问」 | 全屋对了，但**执行类又开始反问**「需要我帮您做其他操作吗」 |
| **v7** | 把「执行后不许有问句」提到铁律 | 执行/查询/单房间全对，但**全屋概况退化**成空洞回答 |
| v8 | 规则全改成第二人称；删掉被复述的那条 | 全屋概况修好，单房间仍多问一句 |
| v9 | 明确列出仅有的两种可带问号的情形 | 拖延话术修好，但**分页的追问被一并杀掉** |
| v10 | 按场景分别指定（单房间/全屋/什么情况） | 三类概况全对，超纲回答变长 |
| v11 | 加「一句话最多数三样东西」这个**可数**约束 | 整体 89% → 93% |
| **v12** | 加「不许编房间名」+「感受类先看状态」 | 20 条里 18 条稳定通过，见下文 |

### ⚠️ 打地鼠：手调的天花板

**每修好一个就坏掉另一个**，七版下来没有一版是全对的。
更要命的是，每一版我只手工验证三四条 —— **看不见其他场景是否被破坏**。
上表 v7 那行的退化，纯粹是这次碰巧测到了才发现的。

这是**评测集优先于一切调优**最直接的论据（详见 `model-tuning.md`）。
没有尺子的时候，你以为在优化，实际在随机游走。

### ⚠️ 字数不是目的，播报时长才是

一开始把铁律写成「不超过四十个字」，本意是别让 TTS 念太久。后来才发现这个换算从没做过。

**实测曼波音色语速 4.54 字/秒**（ffprobe 量的音频时长，四个样本 7～88 字）：

| 字数 | 播报时长 |
|---|---|
| 40 字 | **8.8 秒** ← 原来的铁律 |
| 60 字 | 13 秒 |
| **90 字** | **20 秒** ← 可接受的上限 |

也就是说，原来的限制卡在实际需求的**一半都不到**。

### 「限制太紧会不会让模型偷懒」—— 会，而且证据很干净

同一批问题，40 字上限 vs 90 字上限：

| 问题 | 40 字 | 90 字 |
|---|---|---|
| 客厅都有些什么设备 | 20 字：「灯光、音响、风扇、窗帘和智能面板」← 笼统带过 | 86 字：完整列出十四个设备 |
| 家里现在什么情况 | 28 字，三个区域 | 68 字，五个区域 |
| 汇总书房设备 | 38 字，灯只说「其他灯都关着」 | 47 字，五盏灯逐个点名 |
| **把书房的灯关掉** | 9 字 | **9 字**（没变） |
| **书房还有哪些灯没关** | 26 字 | **26 字**（没变） |

关键是最后两行：**放宽只影响「装不下」的问题，装得下的一个字没多**，
不存在「放开就变啰嗦」的副作用。

但要分清楚它改善了什么：**长度限制是输出预算，不是思考预算**
（何况 `think` 已经关了）。放宽能让枚举和概况类答完整，
**改善不了推理正确性** —— 幻觉「书房灯带」、感受类不查状态、命名匹配失败，
这三样在 90 字下一模一样。

### ⚠️⚠️ 加规则的代价：提示词越长，模型越敢编

为了配合放宽又补了几条规则，结果撞出一个比啰嗦严重得多的问题。
同一条用例「把车库的灯关掉」（家里没有车库），每版跑 5 次：

| 版本 | 提示词长度 | 不谎报执行成功 |
|---|---|---|
| v10 | 389 字 | **5/5** |
| v12 | 507 字 | 3/5 |
| v14 | 529 字 | **1/5** |

模型开始回答「车库的灯已经关闭。」—— **凭空编造出一次成功的执行**。
这比回答太长危险得多：用户会以为灯关了。

**提示词每加一条规则，别处的服从度就掉一点**，而且掉在哪儿事先不知道。
这是前面「提示词越短越服从」那条规律的最硬证据，代价也最重。

反过来压缩也不行：v15 把 v14 砍到 364 字，把「什么时候该反问」三行并成一段，
结果模型**完全不反问了**（`err-ambiguous` 0/5）。**行结构和具体措辞同样在起作用**，
不是单纯的字数游戏。

### 结论：长尾压不住，该换手段了

最终采用 v16 —— v10 原样，只把「四十」改成「九十」，别的一个字不动：

| 版本 | 提示词 | 回答上限 | 整体通过率 | 全败用例 |
|---|---|---|---|---|
| v14 | 529 字 | 90 字 | 88% | 0 |
| v15 | 364 字 | 90 字 | **82%** | 3 |
| **v16** | **389 字** | **90 字** | **88%** | **0** |

但放宽之后**长尾失控了**：出现 202 字、216 字的回答，
按 4.54 字/秒就是 **45～48 秒**，比原来的问题更糟。
40 字铁律虽然让模型偷懒，却顺带把尾巴压住了。

**所以提示词这条路到头了。** 一度打算在 `wyoming_manbo_tts.py` 里按句切分做硬分页 ——
播够 ~90 字就停，剩下的等用户说「继续」。100% 可靠，不占提示词预算。

**但这个方案被否掉了，理由很硬**：万一要的就是「念一篇长文章」呢？

TTS 层**不知道用户在干什么**。它只看见一串待合成的字，分不清这是
「汇总一下全家设备」（该分页）还是「把这篇文章念给我听」（不该分页）。
在这一层做硬截断，等于用一条规则同时管两种相反的需求。

**截断策略必须由知道意图的那一层来定**。真要做，也该是对话层在返回文本时
附带一个「这段可不可以截」的标记，TTS 只负责执行 —— 而不是 TTS 自己拍板。

**当前决定：不做，先受着。** 理由：
- 长尾（200+ 字）只在「全家概况」这一类低频问题上出现，日常指令一个字没多
- 朗读长文本是明确会有的需求，现在把路堵死，回头要拆
- 真正该先做的是**改名**和**评测走真实管线**，那两件的收益确定得多

⚠️ 记下这条，是因为「在错误的层做正确的事」很容易看起来像个好主意。

### 有尺子之后：从 v7 到 v12

评测集建起来之后（`scripts/run_eval.py`，20 条，跑一轮 80 秒），
调提示词从「碰运气」变成了「看数字」。v8→v12 五个版本每一版都是先改一条、
再跑一遍、留下涨的：

```
v10  整体 89%   ← 稳定 15/18，超长是唯一失败模式
v11  整体 93%   ← 只加了一句「一句话最多数三样东西」
v12  整体 92%   ← 20 条里稳定通过 18（新增两条感受类都过）
```

v9 那次尤其说明问题：修好了拖延话术，却把分页的追问一起杀了 ——
**放在从前这个破坏根本不会被发现**，因为手工只会去验刚改的那条。

**当前状态**：v12 在用，20 条里 18 条稳定通过。剩下的：

| 用例 | 状况 |
|---|---|
| `multi-expand-paging` | 0/3，展开时超长（46–95 字），字数铁律在枚举场景下压不住 |
| `exec-turn-*` | 偶尔多问一句，2/3 ~ 3/3 波动 |

两条都是**超长**。字数是模型数不准的东西 —— 换成可数的约束（「最多数三样」）
有明显效果，但没有根治。再往下要么接受，要么去动架构（分层路由）而不是提示词。

## 二、给 AI 用的实体命名

### 为什么命名突然重要了

给人看的界面里，名字难看只是难看。接入 LLM 之后它有三重成本：

| 成本 | 实测依据 |
|---|---|
| **token** | 每个实体约 **32 token**，其中大半是名字。名字长一倍，整个 prompt 就贵一截 |
| **识别** | STT 会听错同音字。实测「书房」被听成「修房」、「猫砂」听成「猫虾」 |
| **准确率** | 名字相近会让 LLM 选错。实测它曾编造出不存在的 `name:"台灯1"` 去关书房的灯 |

### ⚠️ 先说结论：命名不是优化，是**功能正确性**

上面那张表把命名的成本列成「token / 识别 / 准确率」，这个说法**低估了**。
2026-08-16 的评测暴露出：名字不对，设备就是**控制不了**。

| 实体 | 改名前 | 「打开它」成功率 | 改名后 | 成功率 |
|---|---|---|---|---|
| 卧室风扇 | `风扇␠␠风扇` | **0 / 6** | `卧室风扇` | 4 / 4 |
| 书房空调 | `米家空调 自然风Pro 1.5匹 超一级能效␠␠空调` | **0 / N** | `书房空调` | 4 / 4 |

改的**只有名字**，提示词、暴露面、模型一个没动。

原因：LLM 调 `HassTurnOn` 时填的是 `name`，它按用户的说法填「风扇」「空调」，
而 HA 拿这个名字去匹配 `friendly_name`。友好名是 **设备名 + 实体名拼接**出来的，
米家集成两段都叫「风扇」，于是变成 `风扇␠␠风扇`，匹配不上，工具调用直接失败。

对照组很关键：**同一句话给内建意图代理是 6/6 成功**。内建代理走
`area + domain` 匹配，不依赖名字；LLM 走 `name`，所以只有 LLM 这条路会挂。
换句话说，**接入 LLM 之前这个命名问题是隐形的**。

### 工具调用失败之后，模型会去复述提示词

比命名失败本身更难查的是它的表现形式。风扇那六次失败里，模型说的是：

```
设备没找到，是哪个房间？          ← 看起来像正常的错误处理
参数错误，无法执行。               ← 看起来像 HA 报的错
执行开关操作，句号收尾。            ← 提示词铁律二的原文
```

第三句才是线索：**「执行开关操作，句号收尾」是提示词里的规则，不是回答**。
模型调工具失败、没话可说时，会从上下文里捞最近的一句话交差 ——
而系统提示词里全是短促的中文陈述句，个个都长得像可用的回复。

同一现象的另一个样本：v7 提示词里有一行「找不到设备就说找不到，反问是哪个房间。」
问「汇总一下全家的设备信息」时，模型**连续 5 次**回答「找不到设备，反问是哪个房间。」

**规避办法（v8 起采用）**：

1. **规则一律写成第二人称**（「你不能…」「你要…」），别写成无主语的祈使句。
   祈使句和回复长得一样，第二人称不会。
2. **删掉那些「模型没得答时最省事的兜底句」**。「找不到就说找不到」这条纯属多余 ——
   工具自己会返回找不到，写进提示词只是给它一句现成的话去抄。
3. 第二人称能大幅减轻但**根治不了**。真正的根治是让工具调用别失败，也就是改名。

### 命名规则

**R1 名字要「说得出口」**

判据很简单：**你会这么跟人说话吗？**

```
❌ 窗边三开  吸顶灯 左键
✅ 书房吸顶灯
```

**R2 结构用「区域 + 负载」，不要带控制器**

用户关心的是被控制的东西，不是控制它的开关面板在哪面墙上。

```
❌ 卧室门口智能面板  舞台灯带 开关
✅ 舞台灯带
```

区域信息 HA 会自动带（实体的 area 归属会进 prompt），名字里通常不必重复，
除非同名负载分布在多个区域（比如三个房间都有「吸顶灯」）。

**R2b ⚠️ 区域前缀会把指令从「内建快路」推到 LLM（别无脑加前缀）**

管线上 `prefer_local_intents=True`，HA 会先用内建句式匹配，命中就 ~0.1s 返回、
根本不进 LLM。但加了区域前缀的名字会破坏这个匹配：

| 说法 | 处理层 | 耗时 |
|---|---|---|
| 把书房的**循环扇**打开 | LLM | 1.31s |
| 打开书房循环扇 | **内建** | 0.24s |
| 把书房的**风扇**打开 | **内建** | 0.22s |

实体叫「书房循环扇」时，说「把**书房的**循环扇打开」——句式里的区域槽填了「书房」，
剩下「循环扇」去匹配名字，而名字是「书房循环扇」，对不上，只能落给 LLM。
而「风扇」是**域的通用词**（fan），走「区域＋域」匹配，永远能中。

所以：

- **通用类别词（灯 / 风扇 / 窗帘 / 空调）不用管**，天然走内建
- **具体设备名只在跨区域重名时才加区域前缀**（三个房间都有「吸顶灯」那种）
- 单个区域内独一份的负载，用**裸名**（「循环扇」而不是「书房循环扇」），
  区域信息 HA 自己会带

还有一条内建层的固有限制要知道：**它匹配到「区域＋域」时不区分具体设备**。
实测「打开书房吸顶灯」0.08s 命中内建，但回的是「书房灯已打开」——
**把书房所有灯都开了**。要精确控制单个设备，反而得让它走 LLM。

**R3 同区域内避免同音和近音**

STT 是整条链路里最脆弱的一环。同一区域里如果有「壁灯」和「壁柜灯」，
识别错一个字就指向另一个设备。这类冲突要么改名拉开距离，要么靠别名补一个更好念的说法。

**R4 名字里不要出现纯技术词**

`左键 / 中键 / 右键 / P1S_01P00C4A2700361 / 开关 开关` —— 这些对 LLM 是噪音，
对用户是听不懂，唯一的作用是消耗 token。

⚠️ **但删除它们要当心**：本宅实测中，`左键/中键/右键` **恰恰是多路开关真继电器的名字**，
不能因为名字难看就把实体删了或不暴露 —— 详见 `docs/exposure-policy.md` 的 R3。
正确做法是**改名**，不是排除。

**R5 别名是补充，不是替代**

改名和加别名解决的是不同问题：

| | 用途 |
|---|---|
| **改名** | 让 LLM 拿到的清单更短更清晰。**省 token，提准确率** |
| **别名** | 给同一个设备加上口语说法（「外面的灯」「大灯」）。**不省 token，提召回** |

两者都要做：先把名字改对，再给高频设备加一两个口语别名。

**R6 别名优先给「说法固定的模糊词」**

蓝图第 04 节的原则：**说法固定的模糊词用别名（快），随场景变化的歧义才留给 LLM（聪明）**。
「外面的灯」永远指阳台加入户走廊，那就写成别名，让反射层半秒命中；
「有点暗」这种依赖当下情境的，才值得让 LLM 去理解。

| 目的 | 位置 |
|---|---|
| 改实体名 | 实体详情 → 齿轮 → 名称 |

### 落地建议

不必一次改完。按这个顺序性价比最高：

1. **先改暴露集合里的**（本宅 83 个）—— 没暴露的实体改了对 AI 毫无影响
2. **先改 `switch_as_x` 转出来的那批**（本宅 24 个）—— 它们的名字最难看，
   形如「窗边三开 吸顶灯 左键」，而且都是高频灯具
3. **再给最常说的十来个加别名**
