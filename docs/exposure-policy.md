# 实体暴露策略

「哪些实体该暴露给 Assist / LLM」的判定规则。2026-08-16 从本宅 435 个暴露实体的实测中沉淀。

## 为什么要治理

本宅治理前的实测（435 个暴露实体）：

| 指标 | 数值 |
|---|---|
| 实体清单字符数 | 38,577 |
| 估算 token | **~14,245** |
| 平均每实体 | 88 字符 / **~32 token** |
| prefill 耗时（8B Q4 @ 5060 Ti，按 3000 tok/s 估） | **~4.7s** |

三重代价：

1. **延迟** —— 每次对话都要重新处理这 1.4 万 token，而语音场景给 LLM 的整段预算只有 300ms–2s
2. **缓存失效** —— 清单里带实时状态，任一实体翻转就打穿 KV 缓存前缀，长清单还更难被缓存住，是乘法效应
3. **准确率** —— 候选越多越容易选错，且错误往往隐蔽（改了「开灯默认状态」而不是关灯，当场看不出来）

**单价好记：每实体约 32 token。** 加 10 个设备 ≈ 多 320 token ≈ 多 0.1 秒。

## HA 官方的默认规则

源码 `homeassistant/components/homeassistant/exposed_entities.py`：

```
先排除：entity_category ≠ None  或  hidden_by ≠ None
再纳入：domain ∈ { climate, cover, fan, humidifier, light, media_player,
                  scene, switch, todo, vacuum, water_heater }
        或 binary_sensor.device_class ∈ { DOOR, GARAGE_DOOR, LOCK, MOTION,
                                          OPENING, PRESENCE, WINDOW }
        或 sensor.device_class ∈ { AQI, CO, CO2, HUMIDITY, PM10, PM25,
                                   TEMPERATURE, VOC }
```

两条推论：

- **`lock` 不在默认列表里** —— 门锁天然不会被自动暴露，安全约束 HA 已经守住
- **`hidden_by` 与 `entity_category` 是等价排除项** —— 隐藏一个实体等于让它永不被自动暴露

### 本宅 435 个的根因

**小米系集成把设备设置项建成了 `switch` 实体，却没有标 `entity_category: config`。**
厂商若标了，HA 会自动排除。352 个 switch 里，真正可控的只有约 30 个，其余全是
「防闪烁模式 / 左键 / 物理控制锁 / 提示音 / 通电默认状态」这类内部设置。

这是集成的实现问题，不是配置问题——所以**只能靠下面的补充规则兜底**。

## 补充规则（官方规则覆盖不到的）

### R1 域白名单不够，要叠名称过滤

`switch` 在官方白名单里，但厂商会往里塞设置项。需要一份特征词表做二次过滤：

```
防闪烁 左键 右键 中键 物理控制锁 提示音 延时 睡眠模式 通电默认状态
唤醒自定义 助眠自定义 勿扰 开灯默认状态 静音 遥控器 凌动开关 指示灯
童锁 自定义开关 蜂鸣 屏幕显示 记忆 校准 复位 重置 固件 灵敏度
```

还有一类特征更明显：**实体名本身就是开发者写的字段描述**，例如
「状态，true：启用中；false：未启用」「显示按键名称；true为显示」——见到即删。

### R2 按设备型号判断，不看名字

同样叫「开关」，语义可能完全相反：

| 型号 | 类型 | 继电器语义 |
|---|---|---|
| `cuco.plug.v3`、`chuangmi.plug.212a01` | 智能插座 | 继电器 **就是** 控制手段，安全 |
| `lemesh.switch.*`、`xiaomi.switch.pro1` | 墙壁开关 / 低压通断器 | **取决于模式**，见 R3 |
| `xiaomi.controller.86v1` | 中控面板 | **混合** —— 多路灯继电器 + 一堆屏幕/音效设置项，须落到实体粒度，见 R4d |

### R3 墙壁开关必查无线模式

米家智能开关有「无线模式」：继电器常闭给下游智能灯供电，按键只发无线事件驱动自动化。
**此时若调用 `switch.turn_off`，智能灯直接断电、无线模式同时失效。**

判定方式（部分型号可读）：

```
select.<设备> 开关 模式  = 有线开关 / 无线开关 / 有线和无线开关
```

- **「有线」或「有线和无线」** → 继电器受按键控制，可暴露
- **纯「无线开关」** → 继电器不可暴露，改暴露下游的 `light` 实体
- **无此实体**（如 `lemesh.switch.sw0a04`）→ HA 侧判不了，必须问人

⚠️ 这些 `select` 实体常在噪音治理时被隐藏，**但隐藏不影响读取**，脚本照样能查。

### R4 单火线是佐证

```
sensor.<设备> 开关 接线方式 = No Neutral
```

单火开关靠负载取电，**不可能跑纯无线模式**，所以可以放心暴露继电器。

### R4b 名称里的 ` * ` 是厂商自定义服务标记

xiaomi_home 集成用 ` * ` 标记「非标准 MIoT 服务」。实测 435 个暴露实体中 **132 个含 `*`**，
几乎全是设置项：

```
植物墙水泵  开关 开关              ← 主继电器（无 *）
植物墙水泵 * 充电保护 开关          ← 设置项
植物墙水泵 * 快捷倒计时关闭 …开关    ← 设置项
植物墙水泵 * 最大功率限制 开关       ← 设置项
植物墙水泵 * 过度用电提醒 开关       ← 设置项
```

一个 `*` 就能滤掉三成噪音，成本极低，**建议作为第一道过滤**。
但它不充分——不含 `*` 的里面仍有大量设置项（凌动开关、夜灯开关、遥控器管理），要叠 R1 词表。

### R4c 真继电器的判据：功能段是「开关」或「电源」

在 `switch` 域里，实体名的最后一段若恰为「开关」或「电源」，且前一段是**负载名**
（吸顶灯 / 玄关柜灯带 / 水泵）而非功能名，那才是真继电器。本宅 352 个 switch 里
最终只有 **26 个**符合。

⚠️ 例外：形如「…制热达温停机改善开关」这种尾字碰巧是「开关」的设置项会漏网，仍需人工过一眼。

### R4d 别把「面板」一概当设置项

`xiaomi.controller.86v1`（智能家庭面板）**同时是多路墙壁开关** ——
它既有一堆屏幕/音效设置项，也有若干路真实的灯继电器。按设备整体判断会误杀，
必须落到实体粒度。

### R5 重复控制路径只留一个

同一负载既有 `light` 实体又有插座 `switch` 实体时，LLM 面对「关落地灯」不知道调哪个。
留语义更准的那个（通常是 `light`），另一个移除。

### R6 后果不可逆的不暴露

水泵、雾化器、CO2、加热类——误关可能造成不可逆损失（缸内生物死亡），
而 **LLM 无法评估这类后果**。这类设备走自动化，不进语音视野。

### R7 查询类不常驻 prompt

`sensor` / `binary_sensor` 即使在 device_class 白名单里，也不必常驻——
LLM 需要时用 `GetLiveContext` 按区域/域按需查即可，那是工具调用，不占 system prompt。

## 操作入口

| 目的 | 位置 |
|---|---|
| 批量增删 | 设置 → 语音助手 → 「暴露」标签页 |
| 单实体 + 别名 | 实体详情 → 齿轮 → 「语音助手」区块 |
| **默认策略「暴露新实体」** | 同上页面 —— **不关掉，砍完还会长回来** |
| 程序化 | WebSocket `homeassistant/expose_entity/set` |

**最关键的是第三条。** 每接入一台米家设备，它十几个子开关会全部自动进入暴露集合——
本宅 435 个就是这么积累的。关掉之后流程变成「新设备默认不暴露，需要语音控制时主动加」，
多一步手工，换来暴露集合永远只含你真正想让 LLM 碰的东西。

## 复现

```bash
python scripts/measure_exposure.py    # 量当前暴露面的 token 体积
python scripts/classify_exposure.py   # 按上述规则分成 保留/待定/移除
```

分类结果写 `exposure_plan.json`，**先人工过目再执行**——
批量变更遵循蓝图第 13 节「习惯自动化必须人工确认」的同一原则。
