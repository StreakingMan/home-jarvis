# 实体暴露策略

「哪些实体该暴露给 Assist / LLM」的判定规则。2026-08-16 从本宅 435 个暴露实体的实测中沉淀。

## 为什么要治理

本宅治理前的实测（435 个暴露实体）：

| 指标 | 数值 |
|---|---|
| 实体清单字符数 | 38,577 |
| 估算 token | **~14,245** |
| 平均每实体 | 88 字符 / **~32 token** |
| prefill 耗时（8B Q4 @ 5060 Ti，按 3000 tok/s 估） | **~4.7s** |

三重代价：

1. **延迟** —— 每次对话都要重新处理这 1.4 万 token，而语音场景给 LLM 的整段预算只有 300ms–2s
2. **缓存失效** —— 清单里带实时状态，任一实体翻转就打穿 KV 缓存前缀，长清单还更难被缓存住，是乘法效应
3. **准确率** —— 候选越多越容易选错，且错误往往隐蔽（改了「开灯默认状态」而不是关灯，当场看不出来）

**单价好记：每实体约 32 token。** 加 10 个设备 ≈ 多 320 token ≈ 多 0.1 秒。

## HA 官方的默认规则

源码 `homeassistant/components/homeassistant/exposed_entities.py`：

```
先排除：entity_category ≠ None  或  hidden_by ≠ None
再纳入：domain ∈ { climate, cover, fan, humidifier, light, media_player,
                  scene, switch, todo, vacuum, water_heater }
        或 binary_sensor.device_class ∈ { DOOR, GARAGE_DOOR, LOCK, MOTION,
                                          OPENING, PRESENCE, WINDOW }
        或 sensor.device_class ∈ { AQI, CO, CO2, HUMIDITY, PM10, PM25,
                                   TEMPERATURE, VOC }
```

两条推论：

- **`lock` 不在默认列表里** —— 门锁天然不会被自动暴露，安全约束 HA 已经守住
- **`hidden_by` 与 `entity_category` 是等价排除项** —— 隐藏一个实体等于让它永不被自动暴露

### 本宅 435 个的根因

**小米系集成把设备设置项建成了 `switch` 实体，却没有标 `entity_category: config`。**
厂商若标了，HA 会自动排除。352 个 switch 里，真正可控的只有约 30 个，其余全是
「防闪烁模式 / 左键 / 物理控制锁 / 提示音 / 通电默认状态」这类内部设置。

这是集成的实现问题，不是配置问题——所以**只能靠下面的补充规则兜底**。

## 补充规则（官方规则覆盖不到的）

### R1 域白名单不够，要叠名称过滤

`switch` 在官方白名单里，但厂商会往里塞设置项。需要一份特征词表做二次过滤：

```
防闪烁 物理控制锁 提示音 延时 睡眠模式 通电默认状态 唤醒自定义 助眠自定义
勿扰 开灯默认状态 静音 遥控器 凌动开关 指示灯 童锁 自定义 蜂鸣 屏幕 夜灯
记忆 校准 复位 重置 固件 灵敏度 保温 除氯 风冷 开发者模式 识别 地毯 拖布 …
```

⚠️ **词表里绝不能放「左键 / 中键 / 右键」** —— 多路开关的真继电器就叫这个名字，
放进去会误删（本宅会误删 15 路，卫生间全部 4 路灯将失去语音控制）。见 R3。

⚠️ 词表只是**第 3 步**的兜底。多路开关必须先走 R3 的 siid + 模式判定，
名称词表在那类设备上既误删又漏判。

还有一类特征更明显：**实体名本身就是开发者写的字段描述**，例如
「状态，true：启用中；false：未启用」「显示按键名称；true为显示」——见到即删。

### R2 按设备型号判断，不看名字

同样叫「开关」，语义可能完全相反：

| 型号 | 类型 | 继电器语义 |
|---|---|---|
| `cuco.plug.v3`、`chuangmi.plug.212a01` | 智能插座 | 继电器 **就是** 控制手段，安全 |
| `lemesh.switch.*`、`xiaomi.switch.pro1` | 墙壁开关 / 低压通断器 | **取决于模式**，见 R3 |
| `xiaomi.controller.86v1` | 中控面板 | **混合** —— 多路灯继电器 + 一堆屏幕/音效设置项，须落到实体粒度，见 R4d |

### R3 多路开关：先按 siid 分路，再读该路的模式 ★最重要

米家智能开关有「无线模式」：继电器常闭给下游智能灯供电，按键只发无线事件驱动自动化。
**此时调用 `switch.turn_off`，智能灯直接断电、无线模式一并失效。**

关键在于**一个面板有 1–3 路（单开/双开/三开），每一路可以独立设成无线**，
所以必须逐路判断，不能按设备整体判断。

**分路方法**：xiaomi_home 的 entity_id 尾部编码了 MIoT 的 `_p_<siid>_<piid>`，
**同一路的实体共享 siid** —— 该路的模式 `select`、继电器 `switch`、防闪烁设置
都挂在同一个 siid 下。按名字子串匹配会串味（「左键」会匹配到「左键 防闪烁模式」），
**必须按 siid 配对**。

**判据是模式实体的值，不是名字**：

| 值 | 处理 |
|---|---|
| `无线开关` | 该路继电器**绝不暴露** |
| `有线开关` / `有线和无线开关` | 该路继电器就是真控制手段，**暴露** |
| 无模式实体 | 落到型号和名称判断 |

⚠️ **两个反直觉的坑**（本宅实测）：

1. **「左键 / 中键 / 右键」往往就是真继电器**，不是按键配置项。
   本宅有 15 路有线继电器叫这个名字，其中卫生间全部 4 路灯都靠它们控制——
   按名称词表过滤会把它们全删掉，那几盏灯就永久失去语音控制。
2. **同一面板逐路模式可以不同**。例如某三开面板：「筒灯」那路是有线（接哑负载），
   「中键 / 右键」两路是纯无线（接智能灯，用来触发自动化）。这很合理，也很常见。

本宅实测：**29 路纯无线**（必须排除）、**15 路有线**（必须保留），
两类都被 v1 的名称词表判错了——一个漏判、一个误删。

⚠️ 模式 `select` 实体常在噪音治理时被隐藏，**但隐藏不影响读取**。

### R4 单火线是佐证

```
sensor.<设备> 开关 接线方式 = No Neutral
```

单火开关靠负载取电，**不可能跑纯无线模式**，所以可以放心暴露继电器。

### R4b 名称里的 ` * ` 是厂商自定义服务标记

xiaomi_home 集成用 ` * ` 标记「非标准 MIoT 服务」。实测 435 个暴露实体中 **132 个含 `*`**，
几乎全是设置项：

```
植物墙水泵  开关 开关              ← 主继电器（无 *）
植物墙水泵 * 充电保护 开关          ← 设置项
植物墙水泵 * 快捷倒计时关闭 …开关    ← 设置项
植物墙水泵 * 最大功率限制 开关       ← 设置项
植物墙水泵 * 过度用电提醒 开关       ← 设置项
```

一个 `*` 就能滤掉三成噪音，成本极低，**建议作为第一道过滤**。
但它不充分——不含 `*` 的里面仍有大量设置项（凌动开关、夜灯开关、遥控器管理），要叠 R1 词表。

### R4c 真继电器的判据：功能段是「开关」或「电源」

在 `switch` 域里，实体名的最后一段若恰为「开关」或「电源」，且前一段是**负载名**
（吸顶灯 / 玄关柜灯带 / 水泵）而非功能名，那才是真继电器。本宅 352 个 switch 里
最终只有 **26 个**符合。

⚠️ 例外：形如「…制热达温停机改善开关」这种尾字碰巧是「开关」的设置项会漏网，仍需人工过一眼。

### R4d 别把「面板」一概当设置项

`xiaomi.controller.86v1`（智能家庭面板）**同时是多路墙壁开关** ——
它既有一堆屏幕/音效设置项，也有若干路真实的灯继电器。按设备整体判断会误杀，
必须落到实体粒度。

### R5 智能开关接智能灯时，留智能灯

**本宅原则**：同一负载既有 `light` 实体又有继电器 `switch` 实体时，**一律留 `light`**。
理由是 `light` 语义更准（能调亮度色温），且避免 LLM 在「关灯」时二选一。

⚠️ 判定时当心假阳性：开关面板和插座自己带的 **`指示灯`** 也是 `light` 域，
但那是面板状态 LED，不是被控负载。它们 `entity_category: config`、本就不会被暴露，
**按名字匹配会误判成重复**，需按 `entity_category` 排除后再比。

### R5b 米家的「标记为灯」HA 读不到，用 switch_as_x 补

米家 App 里可以把开关的某一路标记为灯，小爱据此让「关某房间所有灯」包含它。
但那是**米家云端/App 层的属性，不在 MIoT spec 里** —— xiaomi_home 集成只看到
一个 `switch:on` 属性，如实映射成 `switch` 实体（实测 `device_class: switch`，
没有任何品类线索）。

后果：HA 的「关某区域所有的灯」不含这些继电器，LLM 拿到的语义也是 switch。

**解法是 HA 内置的 `switch_as_x` 助手**，把 switch 重新包装成 light：

```
配置流 handler = switch_as_x
参数：entity_id / target_domain（cover|fan|light|lock|siren|valve）/ invert
```

转换后 HA 会自动把原 switch 置为 `hidden_by=integration`，
并**把暴露设置一并迁移到新实体**（实测 25 转 25，暴露总数不变）。
这正好满足 R5「重复控制路径只留一个」。

本宅 2026-08-16 转了 24 个（22 → light，2 → fan），效果：

| | 转换前 | 转换后 |
|---|---|---|
| 暴露的 light | 30 | **51** |
| 暴露的 switch | 38 | 13 |
| 书房的「灯」 | 1 盏 | **5 盏** |
| 卫生间的「灯」 | **0 盏** | 3 盏 |

⚠️ **植物灯不要转**：转成 light 后会被「把灯都关了」误伤，见 R6。
本宅的雨林灯、猪笼草缸相关继电器保持 switch。

见 `scripts/switch_as_light.py`。

### R6 后果不可逆 **且指令易混淆** 才不暴露

原先的表述是「后果不可逆就不暴露」，**实践中过严**。
水泵、雾化器、CO2 这类虽然误关后果重，但**指令本身极其明确**
（「打开鱼缸水泵」不会和别的设备混淆），误操作概率低，可以暴露。

真正该排除的是「后果重 **且** 容易被泛化指令误伤」的组合——
典型是**混在灯组里的植物灯**：一句「把灯都关了」就会连带关掉。

所以判据是两条同时成立，不是任一。

### R7 查询类不常驻 prompt

`sensor` / `binary_sensor` 即使在 device_class 白名单里，也不必常驻——
LLM 需要时用 `GetLiveContext` 按区域/域按需查即可，那是工具调用，不占 system prompt。

## 操作入口

| 目的 | 位置 |
|---|---|
| 批量增删 | 设置 → 语音助手 → 「暴露」标签页 |
| 单实体 + 别名 | 实体详情 → 齿轮 → 「语音助手」区块 |
| **默认策略「暴露新实体」** | 同页右上角 ⋮ 菜单 —— **不关掉，砍完还会长回来**（本宅已于 2026-08-16 关闭） |
| 程序化 | WebSocket `homeassistant/expose_entity`（**无 `/set` 后缀**，见下方备忘） |

**最关键的是第三条。** 每接入一台米家设备，它十几个子开关会全部自动进入暴露集合——
本宅 435 个就是这么积累的。关掉之后流程变成「新设备默认不暴露，需要语音控制时主动加」，
多一步手工，换来暴露集合永远只含你真正想让 LLM 碰的东西。

## 复现

```bash
python scripts/measure_exposure.py    # 量当前暴露面的 token 体积
python scripts/classify_exposure.py   # 按上述规则分成 保留/待定/移除
```

`classify_exposure.py` 默认只打印，加 `--apply` 才实际生效；
执行前会把原始暴露集合备份到 `exposure_backup.json`，可据此回滚。

**先人工过目再执行**——批量变更遵循蓝图第 13 节「习惯自动化必须人工确认」的同一原则。

### WebSocket 命令备忘

```
homeassistant/expose_entity/list                    读当前暴露集合
homeassistant/expose_entity                         设置暴露（注意：无 /set 后缀）
    assistants: ["conversation"]  entity_ids: [...]  should_expose: bool
homeassistant/expose_new_entities/get   {assistant}
homeassistant/expose_new_entities/set   {assistant, expose_new}
```

均需管理员权限。长期令牌走 WebSocket 可用，REST 的 `/api/hassio/*` 则一律 401。

## 隐藏 ≠ 解除暴露

两者是**独立的开关**，HA 只在实体**首次出现**时用 `hidden_by` 推导默认暴露值：

```
async_should_expose:
  1. options 里有显式 should_expose？ → 直接用，不再计算
  2. 没有 → 按默认规则算一次（这时才看 hidden_by / entity_category / 域白名单）
  3. 把结果存进 options —— 从此固化
```

**HA 没有监听 `entity_registry_updated`**，所以：

| 顺序 | 结果 |
|---|---|
| 先隐藏，后出现的实体 | 算默认值时 `hidden_by` 已在 → 不暴露 ✅ |
| **先暴露，后隐藏** | 存储值早已固化为 `should_expose: True` → **仍然暴露** ❌ |

> **想让实体不被 LLM 碰，必须显式解除暴露，光隐藏没用。**

反过来，解除暴露的实体在 UI 里依然可见——要清 UI 噪音得单独隐藏。
两个集合也不相同：**隐藏集合 ⊂ 解除暴露集合**，需剔除「真设备但不给 LLM」的部分
（传感器、植物灯、纯无线继电器等，UI 里仍需可见）。见 `scripts/hide_settings_entities.py`。

## 本宅治理结果（2026-08-16）

| | 治理前 | 治理后 |
|---|---|---|
| 暴露实体 | 435 | **83** |
| 清单字符 | 38,577 | 6,748 |
| 估算 token | ~14,245 | **~2,299** |
| prefill 估算 | ~4.7s | **~0.77s** |

同时：

- `expose_new` 设为 `False` —— 新设备不再自动进入暴露集合，否则治理成果会被下一台米家设备稀释回去
- 隐藏了 282 个 `switch` 设置项（2026-08-14 那次噪音治理漏掉的域），已隐藏总数 1519 → 1801
- 保持可见 70 个「真设备但不给 LLM」的实体：31 传感器 / 29 纯无线继电器 / 4 植物灯 / 3 P1S 风扇 / 2 binary_sensor / 1 猫厕所摄像头
