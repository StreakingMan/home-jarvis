## 03 语音 AI 分层架构

核心原则：**快的归本地规则，聪明的归 LLM，慢的归后台 Agent**。千万不要让所有指令都过 LLM。

| 层 | 载体 | 职责 | 延迟 |
|---|---|---|---|
| 反射层 | HA 本地意图引擎（G3 Plus） | 「关外面的灯」「空调 26 度」等高频硬指令。模板+名称槽位严格匹配，断网可用、零 token | < 1 秒 |
| 对话层 | Assist + 本地 LLM（5060 Ti） | 「有点冷，弄暖和点」等理解型指令。流式边生成边播。⚠️ **「本地优先」不是 HA 内置能力**，见下方修正 | 1–3 秒 |
| 认知层 | 外部 Agent（异步） | 记忆、反思、巡检、跨域长任务。不在语音链路上，想明白了经 announce 主动汇报 | 分钟级 · 异步 |

### 组件选型

| 环节 | 选型 | 说明 |
|---|---|---|
| 语音终端 | HA Voice PE（约 ¥400/台） | ESP32-S3 + 双麦 + XMOS 回声消除；设备端 microWakeWord，唤醒后才推流。**无屏幕**，只有 LED 灯环。可多台，各归属一个区域 |
| STT | SenseVoice / faster-whisper（GPU, Wyoming 协议） | 5060 Ti 上短句 <0.5 秒；中文 SenseVoice 优 |
| LLM | Qwen3-14B Q4（Ollama，**关 thinking**） | 40–60 tok/s，首 token ~0.3 秒；云端兜底 DeepSeek/Qwen API |
| TTS | **GPT-SoVITS v2Pro + 「曼波」音色**（2026-08-16 已落地） | 见下方实测。原定 CosyVoice 2 未上岗——GPT-SoVITS 同时满足视频配音与家居播报，一套够用 |

### TTS 实测（2026-08-16，RTX 5060 Ti，曼波音色）

| 指标 | 数值 |
|---|---|
| 模型加载 | 4s |
| 短句合成（「书房的灯已经关好了」） | **0.42s** |
| 长句合成（70 字） | 2.12s |
| 合成实时率 | **6.4x** |
| 显存占用 | 4.4GB |
| 首字延迟 · 整段一次合成 | 3.98s |
| 首字延迟 · **句级流式** | **1.15s** |

三条结论：

1. **不需要为家居另上一套 TTS。** 0.42s 落在延迟预算内，GPT-SoVITS 兼任视频配音与家居播报，CosyVoice 2 不必部署。显存账也宽松：TTS 4.4G + Qwen3-8B 6.5G + whisper 1.6G ≈ 12.5G / 16G，三件套可共存。
2. **句级流式是必须的，不是优化。** 3.98s → 1.15s，差 3.5 倍。实时率 6.4x 远快于播放速度，所以只要第一句能开口，后面永远追得上，零断流。**首句越短开口越快**——这正是「先应一声」人设设计的技术依据。
3. **播放器必须拿到 `Content-Length`。** GPT-SoVITS 的 `api.py` 用 chunked 传输且不带长度，播放器算不出时长、读完第一个 chunk 就停（实测表现为「一句话只播出第一个字」）。解法是前置一层缓冲代理，见 `deploy/README.md`。

部署细节、四个静默失败的坑、systemd unit 均见 `deploy/README.md`。

### ⚠️⚠️ 二次修正（2026-08-16 晚）：`prefer_local_intents` 是存在的，反射层不用自建

**下面那一整节的结论错了，但错法值得留着。**

当初查「Ollama 集成有没有 `prefer_local_intents`」，查的是**对话代理子条目**的字段，
确认只有 `name / model / prompt / llm_hass_api / num_ctx / max_history / keep_alive / think`
—— 这个观察本身没错。错在**找错了对象**：这个开关不在代理上，**在 Assist 管线上**。

```
assist_pipeline/pipeline/list → 曼波管家
    conversation_engine  = conversation.ollama_conversation
    prefer_local_intents = True        ← 就在这儿，而且本来就是开的
```

实测同一句话两条路径（`assist_pipeline/run` vs 直接打对话代理）：

| 指令 | 走管线（真实语音路径） | 直接调 LLM |
|---|---|---|
| 打开书房的灯 | **内建 0.21s** 成功 | LLM 1.23s，幻觉出「书房灯带」**失败** |
| 把书房的灯关掉 | **内建 0.33s** | LLM 1.18s |
| 现在几点 | **内建 0.02s** | LLM 0.84s |
| 书房的灯开着吗 | LLM 1.05s | LLM 1.08s |
| 书房还有哪些灯没关 | LLM 1.33s | LLM 1.32s |

**所以三层架构里的反射层早就在跑了**，高频硬指令比 LLM 快 **6–60 倍**，
一个 `intent-progress` 事件都不产生（这也是判断某条走了哪一层的可靠依据）。

三个连带结论：

1. **路线图第 5 步「自建分层路由」降级** —— 不用造了，反射层已在。
   剩下值得做的是「云端兜底」那条降级链，不是本地路由。
2. **评测必须走 `assist_pipeline/run`** —— 直接打对话代理会绕过内建层，
   测的是一条日常走不到的分支。`scripts/run_eval.py` 已改。
3. **命名策略要跟着变** —— 区域前缀会破坏内建句式匹配，见 `voice-tuning.md` R2b。

⚠️ 教训：**「某个字段不存在」这种结论，要说清楚是在哪个对象上不存在。**
子条目上确实没有，管线上一直有；因为这个，整整半天都在为一个不存在的缺口做设计。

### 分层路由的一次修正（2026-08-16 白天，已被上面推翻）

原表述「管线设『本地优先，未命中落 LLM』」**是错的** —— HA 没有这个能力。实测：

| 代理 | 「把书房的灯关掉」 | Ollama 调用 | 回复来源 |
|---|---|---|---|
| `conversation.home_assistant`（默认） | **0.14s** | 0 | 自动化的 sentence trigger |
| Ollama 对话代理 | 1.05s（热）/ 7.05s（冷） | 2 次 | 模型生成 |

三条事实：

1. **Ollama 集成没有 `prefer_local_intents` 选项** —— 源码确认字段只有
   `name / model / prompt / llm_hass_api / num_ctx / max_history / keep_alive / think`
2. **社区反馈「优先本地处理」自 2025.3 起对 LLM 代理失效**（core#139415、#162768）
3. **`conversation` sentence trigger 只在默认代理下生效** —— 指定 LLM 代理时被完全跳过；
   而 **Assist pipeline 只能选一个代理**

**所以三层架构缺一个「路由器」。** 现成的 `m50/ha-fallback-conversation` 已于
2024-12 归档，对 HA 2026 不可用。

**当前决定：先全走 LLM（方案 A）**，1.05s 落在对话层预算内，零建设成本。
自建路由组件（方案 B）记入路线图第 5 阶段。

**全走 LLM 的代价，按重要性排**：

1. **降级路径缺失（最要命）** —— 游戏模式会主动 `keep_alive:0` 卸载模型，那一刻语音助手失能；
   关机、Ollama 崩了同理。默认代理在 NUC 上 24/7、断网可用。蓝图原本的兜底是「切云端」，
   但那要联网、花钱、且数据出门，与本地部署初衷相悖
2. **延迟 7.5 倍** —— 0.14s 是无感，1.05s 是可察觉的等待；叠加 VAD + STT + TTS 后会压垮 3 秒预算
3. **确定性** —— 实测模型会编造不存在的 `name`（「书房的灯」→ `name:"台灯1"`）
4. **并发** —— `OLLAMA_NUM_PARALLEL=1`，两人同时说话排队；且每条指令走两次推理（tool call 一次、生成回复一次）

### 三条已确认的机制细节

- **Thinking 必须关。** 推理链是念不出来的哑巴 token，思考期间音箱死寂。语音任务（调工具+短回复）14B 无思考绰绰有余；真需要深度推理的问题分流给认知层后台跑。
- **文字与工具调用是穿插的。** LLM 输出是 token 流：「好嘞」（即刻进 TTS）→ tool call（HA 即刻执行，~100ms）→「关好了」（继续播）。实际体感：听到应答时灯已经灭了。多设备指令并行调用。
- **「先应一声」不是默认行为**，要在人设提示词里明确要求；代价是约 0.5 秒开口延迟，换拟人感。

### 端到端语音模型（speech-to-speech）的结论

16GB 显存技术上能跑量化后的 MiniCPM-o 2.6 / Qwen2.5-Omni-7B / GLM-4-Voice，但**不上岗**：工具调用能力弱（智能家居命根子）、HA Assist 管线无接入口、智力弱于级联的 14B 文本模型、显存挤兑。可当玩具体验；等开源 omni 工具调用成熟或 HA 开出 speech-to-speech 代理口子时，只需替换「对话层」一个模块。

## 04 语义消歧与拟人化

### 「外面的灯」问题：别名工程优先

- 本地层是严格匹配：「外面」若不是已知区域/实体/别名，槽位解析失败，**整句安全落到 LLM，不会瞎猜错杀**。
- 最佳实践是主动加别名：给阳台/门廊灯组加「外面的灯」「室外灯」等别名 → 本地层半秒执行。**说法固定的模糊词用别名（快），随场景变化的歧义才留给 LLM（聪明）。**

### 抽象指令的四类分诊：8B 上限之外的活给谁干

「复杂抽象的自然语言指令」是一般语音助手解决不了、也是上 LLM 的核心理由——
但它不是一类问题，是**四类**，每类的正解不同，混在一起才显得无解：

| 类型 | 例子 | 难点 | 出路 |
|---|---|---|---|
| **① 目标态** | 「我要看电影」「准备睡觉了」 | 说的是想要的状态，不是设备动作，需要多步规划 | **离线编译成 scene/script 再暴露**——LLM 的活从「规划」降级成「检索」，一跳完成，8B 稳 |
| **② 身体感受** | 「有点冷」「太闷了」 | 查状态→再决策的两步推理，8B 的已知弱项（见 voice-tuning.md 实测） | **唯一真正留给在线 LLM 的一类**；提示词压症状，认清上限 |
| **③ 集合运算** | 「除了卧室都关了」「没人的房间关灯」 | 工具没有「全部除了 X」语义，模型须枚举+逐个调用，多跳编排易错易误伤 | 建 group（exposure-policy R8）覆盖高频形态；开放式的认怂给云端 |
| **④ 条件时序** | 「洗完衣服叫我」「半小时后关」 | 本质是创建自动化/定时器，不是即时控制 | 分流给 HA timer / 异步认知层，不该在语音层解决 |

于是第 04 节开头那条原则可以细化一层：**留给在线 LLM 的应该只有第 ② 类，
其余三类都有比「指望模型变聪明」更便宜的出路。**

其中第 ① 类和认知层咬合成一个关键闭环：**夜间反思就是目标态指令的「编译器」**——
反思发现「说完'看电影'总是关主灯开氛围灯」→ 经打扰闸门以 `ask` 建议生成 scene →
人确认 → 从此这条抽象指令变成语音层的一跳检索。
**抽象指令的智能不必在线发生，可以离线积累**——「贾维斯感」的来源不是每次都聪明，
是把聪明过的结果存下来了。

剩下的硬核残余（开放式的 ②③），两个待验证的杠杆：

- **升 Qwen3-14B**：显存账本本就按 14B Q4（~10G）规划，现跑 8B。14B 两步推理与多跳
  编排明显更稳，代价 decode 慢 ~40%（74 → ~45 tok/s），短回复场景约多 0.3–0.5s。
  最便宜的升级，动手前后各跑一遍评测集
- **失败即转云端**：游戏模式的云端管线反正要建，复杂指令借道。「判断这题难」本身
  对小模型也难，改用确定性信号——工具调用失败一次即转云端重试

### 给 LLM 的三层上下文

1. **说话人位置**：每台语音卫星归属一个区域，LLM 知道指令来自哪个房间；不带房间名说「开灯」默认操作所在区域。
2. **提示词注入实时状态**：系统提示词是 Jinja 模板，可注入时间、日落、人在传感器分布，以及**家庭词典**（「外面=阳台和入户走廊」这类黑话直接写死）。
3. **结构即上下文**：暴露实体自带区域/楼层归属，命名治理本身就是给 AI 的最大上下文。

### 拟人化：三段流水线逼近端到端体验

ChatGPT 手机端是端到端语音模型，本地 STT→LLM→TTS 天生做不到同款，但两招补掉大半：**口癖在文本层**——人设提示词要求口语化短句、语气词开头；**音色在 TTS 层**——CosyVoice 2 / ChatTTS 支持情感与 `[laughter]`、「嗯」「呃」等副语言 token。配合流式管线可做到 1 秒内开口、全程无空窗。

## 05 安全模型

1. **LLM Tools API 限权**：模型只能通过受限工具集操作，做不到任意 `call_service`。
2. **Expose 白名单**：2806 个实体中只暴露语音需要的几十上百个；门锁、摄像头默认不暴露。**白名单同时是数据边界**——用云端 LLM 时，不暴露即不外泄。
3. **敏感操作走脚本 + 确认**：不暴露锁实体，暴露带条件的脚本；或经 `start_conversation` 二次确认。
4. **令牌隔离**：外部 Agent 用专用令牌可单独吊销；容器隔离运行；规则文件写死「先确认再动作」；**永远不让 Agent 静默修改自动化**。

## 06 贾维斯主动性设计

2025 年后全部为 HA 原生能力：

| 机制 | 能力 | 本宅落地场景 |
|---|---|---|
| `assist_satellite.announce` | 主动播报 | 耗材告警复用仪表板阈值逻辑：「猫厕所 MAX 缺猫砂了」 |
| `assist_satellite.start_conversation` | 主动问询并等回答 | 「客厅灯还开着，需要我关掉吗？」可传 `extra_system_prompt` |
| AI Task（`ai_task.generate_data`） | 定时 AI 分析 | 每日晨间简报；配 LLM Vision 看猫厕所摄像头做异常发现 |

~~**小爱音箱的废物利用**：经 `play_text` 变成「嘴」。~~ **2026-08-16 废弃此方案**——决定全屋统一曼波音色，而 `play_text` 用的是小米云端自己的 TTS，音色改不了。实测三台小米音箱 `supported_features = 17469`，**不含 `PLAY_MEDIA(512)`**，无法播放任意音频 URL，因此在统一音色的前提下完全出局（当不了「耳朵」的结论不变）。

**出口能力矩阵**（决定谁能播曼波）：

| 类 | 能力 | 能否播曼波 | 现状 |
|---|---|---|---|
| A 文本出口 | 只吃文本，自带云端 TTS | ❌ 音色锁死 | 小爱 ×3、面板 ×2 —— **已弃用** |
| B URL 出口 | 播放任意音频 URL | ✅ | HASS.Agent（已通）、DLNA/Chromecast、旧安卓设备 |
| C Assist 卫星 | 走 HA 的 `tts.*` 管线 | ✅ 需先把 GPT-SoVITS 封成 TTS provider | Voice PE（待购） |
| D 推送出口 | 不出声，出字 | — | HA App、Telegram |

**代价**：放弃 A 类等于降级链断了「覆盖广」那一层。**在设备铺齐前会有房间是哑的**，此时闸门的正确行为是记一次「未送达」，而不是换个嗓子说。

## 07 记忆与自我进化

模型本身不会学习——「进化」是外挂的反思循环（reflection loop），发生在每晚的批处理里，不在对话现场：

```
行为数据(HA Recorder/Logbook) → 夜间反思(AI Task: 昨日日志+现有档案→更新档案)
        → 习惯档案(几十行 markdown, 可审计可手改) → 注入语音助手 prompt
```

- **即时记忆**：暴露一个「记住」脚本工具——「记住我不喜欢空调直吹」即追加进档案。
- **习惯 → 自动化必须确认制**：反思任务发现稳定规律后走 `start_conversation` 问询，同意才创建。**建议权给 AI，决定权给人。**
- **防误学**：反思 prompt 要求「至少持续两周的规律才记录」；档案每次合并同类项、删过时项。

## 08 认知层与 OpenClaw

HA 原生 hold 得住「神经系统」（反射/对话/主动播报），hold 不住「大脑皮层」（长期记忆、自主循环、跨域长任务）。答案是分层组合——**且控制力不打折**：Agent 经已开启的 MCP Server 接入，Expose 白名单照样生效，语音快路径完全不经它。

### OpenClaw 开箱即得 vs 需自搭的胶水

**开箱即得**：常驻 daemon + heartbeat 心跳巡检、cron 定时、文件式记忆（markdown workspace）、人格/规则文件、MCP 客户端（填 HA 地址+令牌即通）、Telegram 等消息通道。

**胶水（配置级，非开发）**：反思工作流的提示词；开口出口（经 MCP 调 HA announce → 声音从 Voice PE/小爱出）；分工纪律（语音快路径不经它）。

**清醒预期**：通用 Agent 权限面远大于 HA 内置对话代理，对提示词注入敏感——容器隔离、最小权限令牌、不碰门锁、重要动作确认缺一不可。项目迭代快。云端模型跑心跳+反思月成本几十到一二百元，例行任务可指到本地 Ollama。

**值得抄的三个设计**（即使不用它）：记忆就是普通文本文件（可审计）、用心跳而非被动等事件（自主性来源）、人格单独成文件（可版本管理）。

## 10 游戏与 AI 共存：游戏模式自动化

思路：游戏时自动降级到云端，结束自动切回本地。语音永远可用，帧率零损。

1. **哨兵**：装 HASS.Agent（Windows 伴侣），上报进程/显存占用为 HA 实体。
2. **触发**：检测到游戏进程 / 显存超阈值。
3. **让路**：REST 命令卸载 Ollama 模型（释放 10GB）；Voice PE 的管线选择实体拨到「云端管线」。
4. **复原**：游戏退出后切回本地管线 + 空请求预热模型。

体感：游戏期间复杂指令延迟 1.5 秒 → 3 秒；「关外面的灯」完全无感（反射层在 G3 Plus 上）。CPU 侧游戏吃 P 核、后台服务挤 E 核，天然不冲突。

## 14 认知层框架设计

第 06/07/08 节给出了主动性、记忆、认知层的**能力与骨架**；本节补的是让它长期跑不烂的**约束层**——五处必须先定死的机制，否则实现阶段必返工。

### 14.1 打扰闸门：所有主动动作的唯一出口

第 06 节只规定了「能做什么」，没规定「什么时候该闭嘴」。主动式助手最经典的死法是技术全通、上线一周被嫌烦、然后被永久关掉——而这种失败不可逆，用户对话痨设备的容忍度一旦破产就回不来。

统一签名，所有主动动作强制经此，**任何自动化都不许直接调 `announce` / `start_conversation`**，否则预算形同虚设：

```yaml
script.jarvis_speak:
  fields:
    message:      # 播报内容
    priority:     # info | suggest | ask
    target_area:  # 目标区域：决定在场判定与播报出口
    topic:        # 话题标识：用于衰减、去重，与档案条目共用同一标识
```

判据按序短路：

| 序 | 判据 | 载体 | 不通过 |
|---|---|---|---|
| 1 | 静默窗口（睡眠 / 游戏模式 / 通话中） | `input_boolean` | 丢弃或延后 |
| 2 | 在场判定（目标区域有人） | 小米人在传感器 Pro | 改投他区或丢弃 |
| 3 | 话题衰减（同 topic 被忽略 ≥3 次） | `counter` | 永久静音该 topic |
| 4 | 频率预算（按 priority 分档） | `counter`，每日 0 点重置 | 丢弃 |
| 5 | 出口选择 | — | announce / start_conversation |

优先级分档（起始值，按体感调）：

| priority | 语义 | 出口 | 每日上限 |
|---|---|---|---|
| `info` | 单向告知（耗材、异常） | `announce` | 6 |
| `suggest` | 建议，可无视 | `announce` | 3 |
| `ask` | 要人回答 | `start_conversation` | 2 |

⚠️ 业界通知疲劳经验值是**每日 3–5 条**即触用户关通知的临界点（见 related-work.md）——
上表 suggest+ask=5 已顶上限。建议上线时从半量起步（info 3 / suggest 2 / ask 1），
体感良好再放宽；学术界无正式量化研究，分类型预算本身是本宅原创设计，数字只能实测调。

**出口选择与降级链**（2026-08-16 补，因统一曼波音色而简化）：

原本设想的「音色分级」维度**取消**——全屋统一曼波，`priority` 只决定说不说、说几次，不再决定用谁的嗓子。出口选择退化为一条有序降级链：

```
1. 目标区域内的 B 类出口（能播 URL 且在线）
      ↓ 不可用
2. 邻近区域的 B 类出口（音量降一档）
      ↓ 全部离线 / 目标区域无人
3. HA App 推送（不出声，留记录）
      ↓ 低优先级
4. 丢弃 + 记一次「未送达」
```

第 4 步的「未送达」计数不是废数据——它反过来告诉你哪些播报根本没人听见，是 14.2 评估回路的一个独立信号来源。

**出口注册用标签，不要硬编码。** 给能播 URL 的设备打 `jarvis_out_url`、推送出口打 `jarvis_out_push`，脚本里用 `label_entities()` 动态取。以后加 Voice PE、旧平板、Chromecast **只需打标签，脚本一行不改**。

**接口预留 `short_message`。** 降级到推送出口时自动切换用哪一版文本。现在可以不用，但接口里先留着，免得将来改所有调用方。

**长文本必须句级流式下发**（依据见第 03 节实测）：按 `。！？；` 切句、并发合成、顺序播放，首字延迟 3.98s → 1.15s。

### 14.2 习惯档案格式：从一段文本升级为带状态的条目表

存储在 HA 可读写的纯文本文件（`/config/jarvis/profile.md`），版本管理靠 HA 自动备份，保留第 08 节「记忆就是普通文本文件（可审计）」的原则。

```markdown
- [active] 不喜欢空调直吹
  写入: 2026-08-16 | 依据: 用户直接告知 | 命中: 3 | 否决: 0 | topic: ac_airflow
- [试用] 工作日 23:30 后倾向调暗客厅
  写入: 2026-08-02 | 依据: 观察 11 次 / 3 周 | 命中: 4 | 否决: 2 | topic: night_dim
- [归档] 进门自动开电视
  写入: 2026-07-10 | 否决: 3 | 归档: 2026-08-14 | topic: tv_on_arrival
```

- **状态机**：`试用` --（命中 ≥5 且 否决 =0）--> `active`；任一状态 --（否决累计 3）--> `归档`
- **`topic` 与闸门共用标识** → 记忆淘汰与打扰衰减自动联动，说一次「不用」两边同时降级
- **`命中` / `否决` 是唯一的评估信号来源**——没有它，反思就是开环累积，不是迭代
- **`依据` 可审计**：一眼看出这条是「你说的」还是「它猜的」
- **硬上限 60 条 / 2000 token**：超限时反思任务必须压缩，淘汰序 `归档 > 命中低 > 写入早`。与 Assist 暴露面同理——只增不减的东西迟早撑爆 prompt
- **注入策略**：只注入 `active` + `试用`，归档区不进语音提示词

### 14.3 拒绝也是记忆

反思读的是原始日志，规律一直在，**被拒绝的建议每晚都会被重新发现并重提**——这几乎必然发生，且是最快让人烦的一类失败。

- 用户对某建议说「不用 / 不要」→ 对应 `topic` 否决 +1，落盘
- 反思提示词**必须包含归档区**作为负向清单，指令：「以下已被拒绝，不得再次提出；除非出现明显相反的新证据，且须说明该证据」
- 归档条目**永不删除**，超限时只压缩为一行摘要
- ⚠️ **归档条目须记录拒绝时的上下文**（当时在干什么、拒绝的说法）。推荐系统研究的教训
  （见 related-work.md）：不理解拒绝原因就压制同类建议，泛化很差——「那次不要」≠「永远不要这一类」。
  反思比对负向清单时应做细粒度判断，不是 topic 一刀切

设计要点：**否决必须比确认更省力**。人不会为纠正助手专门做操作，但会顺口说一句「不用」。

### 14.4 职责切分：24/7 的归 HA，可离线的归认知层

| 职责 | 位置 | 触发 | 可离线 |
|---|---|---|---|
| 习惯档案存储 | HA `/config/jarvis/` | — | 否（语音管线要读） |
| 夜间反思 | HA AI Task | 每日 04:00 | 否 |
| 打扰闸门 | HA script + helper | 被调用 | 否 |
| 即时记忆「记住」 | HA script（暴露给 Assist） | 语音 | 否 |
| 跨域长任务 | OpenClaw（GPU 机） | heartbeat / cron | **是** |

原则：**24/7 职责不得依赖非 24/7 的机器**。GPU 机兼职游戏、会关机，故记忆与反思留在 NUC 侧；OpenClaw 只承担可延迟、可失败的长任务。这是第 09 节部署规划的细化而非推翻——OpenClaw 仍在 GPU 机。

反思任务提示词骨架：

```
输入:
  A. 昨日行为日志（Recorder 摘要，仅日志白名单实体）
  B. 档案 active + 试用 条目
  C. 档案归档区（负向清单）
职责（按序）:
  1. 对照 B，更新每条的 命中 / 否决 计数
  2. 从 A 中寻找新规律 —— 门槛：持续至少两周且出现 ≥10 次，不足则不记录
     （措辞注意：这是「疑似规律」的检测门槛，不是「习惯已形成」——
      行为科学测得人类习惯固化中位数 66 天，见 related-work.md；建议话术照此降级）
  3. 新规律与 C 比对，命中则丢弃（除非有明显相反新证据，须说明）
  4. 若超过 60 条或 2000 token，按 归档 > 命中低 > 写入早 压缩
  5. 产出：更新后的档案全文 + 本次建议清单（至多 2 条）
约束:
  - 只输出档案与建议，不得直接创建或修改任何自动化
  - 每条建议须附依据（观察次数、时间跨度）
  - 无新发现是正常结果，允许输出「无」
```

建议清单交由闸门以 `priority: ask` 发出，同意才创建自动化——延续第 13 节「习惯自动化必须人工确认」，**建议权给 AI，决定权给人**。

### 14.5 待定：反思的数据边界

第 05 节「白名单即数据边界」只覆盖语音管线。反思读 Recorder 日志，粒度细得多——几点睡、几点回家、哪天没回家，全在里面。

| 选项 | 做法 | 代价 |
|---|---|---|
| **A** 云端反思 | AI Task 指云端模型 | 行为日志出门；需另立一份「日志白名单」，与 Assist 白名单分开维护 |

### 14.6 有时间依赖的前置动作

| 动作 | 何时 | 拖不得的理由 |

| Recorder 保留期 10 → 30 天 | **开始收集数据之前** | 默认 `purge_keep_days: 10`，「持续两周」的规律永远攒不齐；改晚了要重等两周 |
